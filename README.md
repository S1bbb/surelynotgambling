# Surely Not Gambling

Локальный учебный прототип: 8 игр на виртуальном балансе — Краш, Минёр, Курочка,
Плинко, Рулетка 0–14, Апгрейд, Лестница и Hi-Lo («Больше / меньше»), демо-кошелёк,
Provably Fair, история, статистика и открытая вкладка администратора.
Начальный баланс — 10 000 CR. Реальных денег, депозитов и вывода нет.

## Запуск

Node.js 22.16+ и npm. Из корня:

```sh
npm run setup
npm run build
npm start
```

Адрес: http://127.0.0.1:3000. На Windows можно выполнить `./start.ps1`:
скрипт также находит переносимый Node.js, скачанный во временную папку при разработке.
Для постоянного использования установите Node.js: временный runtime может быть удалён системой.

`npm run dev` запускает API на порту 3000 и интерфейс с HMR на http://127.0.0.1:5173.
Переменные окружения описаны в `.env.example`; файл автоматически не загружается.
Dev proxy рассчитан на API-порт 3000.

## Docker

```sh
docker compose up --build -d
```

Адрес: http://127.0.0.1:3000. Volume `casino-data` сохраняет состояние.

## Hi-Lo: правила и общие условия RTP

- Выпадает целое 0–9999, показанное как 0.00–99.99.
- Порог T: целое 5–95. «Меньше»: R < T×100; «Больше»: R ≥ T×100.
- Вероятность p: T/100 или (100−T)/100. Коэффициент = (RTP/100)/p.
- Полная выплата включает ставку. Суммы хранятся целыми сотыми CR;
  выплаты округляются вниз до 0.01 CR. Поэтому матожидание немного ниже заданного RTP.
- RTP по умолчанию 97%, диапазон настройки 80–99%, шаг 0.01%.
  Меняются выплаты будущих ставок, а не генератор случайного числа.
- RTP, коэффициент, commitment и версия условий фиксируются в каждой ставке.
  Устаревшие условия отклоняются. Изменения RTP журналируются.
- Фактический RTP = выплаты / оборот; на короткой серии может превышать 100%.

## Проверяемая честность: hilo-v1

1. Сервер генерирует 32 случайных байта, использует hex-строку как server seed
   и до ставки публикует SHA-256 этой строки в UTF-8.
2. Игрок задаёт client seed. Nonce каждой ставки увеличивается, начиная с 0.
3. HMAC-SHA256: ключ — **UTF-8 строки** server seed; сообщение —
   `JSON.stringify(["hilo-v1", clientSeed, nonce, cursor])`, cursor начинается с 0.
4. Digest читается группами по 4 байта, unsigned big-endian. Первое число
   меньше 4 294 960 000 даёт `value % 10000`. Остальные отклоняются для удаления
   modulo bias. Если весь digest отклонён, увеличивается cursor.
5. После завершения сессии seed раскрывается, создаётся новый, nonce сбрасывается.
   Браузер независимо воспроизводит результат через Web Crypto, проверяет хеш и выплату.

На защите: сохраните хеш → сделайте ставки → смените RTP → сделайте ещё ставку →
завершите сессию в «Честности игры» → нажмите щит в истории. Проверка старой ставки
использует её исходный RTP. Сохранённый до игры хеш нужен для независимого доказательства
обязательства; интерфейс на сервере оператора сам по себе не защищает от подмены всего приложения.

## Игры: правила, формулы, протоколы

Общее для всех игр: суммы — целые сотые CR, ставка 1–1 000 CR, RTP берётся из
настроек в момент ставки и сохраняется в раунде. Каждая выплата округляется вниз до
0.01 CR **один раз**, поэтому точное матожидание чуть ниже RTP (на ставках по 1 CR это
заметно: например, 96.5% вместо 97% в плинко). Везде HMAC-SHA256 с UTF-8 ключом
server seed; «равномерное число на [0, n)» — uint32 big-endian из digest
`JSON.stringify([протокол, clientSeed, nonce, cursor])` с отбраковкой значений
≥ floor(2^32/n)·n, как в hilo-v1. Один nonce на раунд. Перемешивание Fisher–Yates —
как в stairs-v1 ниже (в сообщении индекс i и cursor, берётся первое uint32 digest).

- **Краш (crash-v1).** u — старшие 52 бита digest `["crash-v1", clientSeed, nonce]`.
  Точка краша в сотых C = floor(R·2^52 / (100·(u+1))), где R — RTP в б.п.; C < 101 → 100
  (мгновенный краш). Отсюда P(C ≥ m) = RTP/m для любого m ≥ ×1.01 с точностью 2^-52.
  Множитель растёт как floor(100·e^(0.00006·t)) по **серверному** времени; вывод на m
  выигрывает, если m ≤ C, выплата = ставка·m. Автовывод ×1.01–×1000; на ×1000 раунд
  закрывается сам. Точка краша не хранится и не отдаётся до конца раунда; раунд,
  чьё время вышло, закрывается при следующем чтении (`GET /api/crash` или `/api/state`).
- **Минёр (mines-v1).** Поле 25 клеток, b = 1–24 бомб — первые b элементов
  перемешанного массива 0–24. После n алмазов шанс следующего (25−b−n)/(25−n),
  выплата = ставка·RTP·C(25,n)/C(25−b,n). Пример с референса: 3 бомбы, RTP 95% →
  ×1.07, 1.23, 1.41, 1.64, 1.91 …
- **Курочка (chicken-v1).** Та же раздача на 25 слотов, машин 1/3/5/10
  (лёгкая/средняя/сложная/безумная), но слоты проходятся по порядку: полоса n —
  слот n−1, полос 25−b. Множители те же, что у минёра; безумная при RTP 96% даёт
  1.60, 2.74, 4.85, 8.90, 16.98, 33.97 (на экране округление вниз: 8.89, 33.96).
- **Плинко (plinko-v1).** Бит на ряд из digest `["plinko-v1", clientSeed, nonce]`
  (от старшего бита, 1 = вправо); лунка k ~ Binomial(ряды, 1/2), 8–16 рядов, риск
  low/medium/high. Форма таблицы задана в десятых и масштабируется:
  множитель(k) = RTP·форма(k)·2^ряды / Σ C(ряды, j)·форма(j), так что Σ P(k)·множитель(k) = RTP ровно.
- **Рулетка (roulette-v1).** Равномерное число 0–14: 0 — зелёное, 1–7 — красные,
  8–14 — чёрные. Цвет платит ставка·RTP·15/7, число — ставка·RTP·15. Несколько фишек
  за спин, в сумме до 1 000 CR.
- **Апгрейд (upgrade-v1).** Равномерное число 0–999 999. Игрок задаёт цель T (×1.10–×1000
  от ставки A); выигрыш, если число < W = floor(10^6·A·R/(10000·T)), выплата T.
  Матожидание T·W/10^6 ≤ A·RTP при любой цели.
- **Лестница (stairs-v2).** Как на референсе: старт ×1 и 12 ступеней, на ступени n
  всего 20−n клеток (19 … 8), на каждую падает k = 1–7 камней. Шанс пройти ступень
  (w−k)/w, выплата = ставка·RTP·Π w/(w−k). При k=1 и RTP 100% получаются x1.05 … x2.71.
  Карта: для каждой строки массив 0…w−1 перемешивается Fisher–Yates, сообщение
  `["stairs-v2", clientSeed, nonce, k, row, i, cursor]`. На вершине выплата автоматическая.

Во всех пошаговых играх (краш, минёр, курочка, лестница) seed нельзя раскрыть, пока
раунд не завершён: иначе стали бы известны будущие исходы. Шаги и вывод идемпотентны,
до конца раунда API не отдаёт ещё не сыгранные исходы.

### Прежняя лестница stairs-v1

Раунды до обновления (8 ступеней × 5 клеток, 1–4 камня) доигрываются и проверяются
по старым правилам: q=(5−K)/5, выплата ставка·(RTP/100)/q^N. Для каждой строки 0–7
массив [0,1,2,3,4] перемешивается Fisher–Yates, i идёт от 4 до 1, сообщение
`JSON.stringify(["stairs-v1", clientSeed, nonce, K, row, i, cursor])`. Первое unsigned
big-endian 32-битное число digest принимается, если меньше `floor(2^32/(i+1))*(i+1)`,
иначе увеличивается cursor. j=value%(i+1), элементы i и j меняются местами; первые K элементов — камни.

## Статистика

Вкладка «Статистика» (и сводка в админке) показывает по каждой игре и в сумме:
оборот, выплаты, итог игрока, фактический RTP, **ожидаемый** RTP, 95% коридор RTP,
σ выплат и отклонение в σ. Для каждого завершённого раунда сервер один раз считает
ожидаемую выплату и дисперсию (`server/stats.mjs`):

- Hi-Lo, рулетка, апгрейд, плинко — точно по полному распределению исходов, с округлением.
- Лестница, минёр, курочка, краш — игрок решает по ходу, поэтому используется
  разложение Дуба стоимости позиции: ожидание = Σ по сделанным шагам
  (шанс·стоимость после шага − стоимость до шага), дисперсия = Σ шанс·(1−шанс)·стоимость².
  Для краша шаги — сетка ×1.01, ×1.02, … до вывода или краша. Оценка несмещённая при
  **любой** стратегии вывода и точно учитывает округление.

Отклонение z = (выплачено − ожидалось)/σ у честной игры ≈ N(0, 1); 95% коридор RTP —
(ожидалось ± 1.96σ)/оборот. Тест `z-score is calibrated` разыгрывает серии со случайными
стратегиями и проверяет, что z действительно имеет среднее ≈ 0 и дисперсию ≈ 1.
Незавершённые раунды в статистику не входят.

## Архитектура

Вкладка «Честность игры» содержит ручной проверяющий экран: server seed, client seed,
nonce, исходный хеш и условия Hi-Lo. Справа выводятся рассчитанное число на шкале,
выигрыш/проигрыш и полная выплата. Хеш и число из истории сравниваются отдельно;
если исходный хеш не указан, обязательство явно считается непроверенным.
Щит в истории подставляет данные ставки. Изменение поля очищает прошлый результат.
Кнопка копирования сохраняет данные в JSON. Сам расчёт выполняется локально через
Web Crypto; для повторного ввода полей сетевой запрос не требуется.

```text
server/fairness.mjs    — генераторы исходов и формулы выплат всех игр
server/common.mjs      — общие проверки ставки, идемпотентность requestId
server/service.mjs     — Hi-Lo, кошелёк, настройки, seed-сессии, снимок состояния
server/ladder.mjs      — лестница (stairs-v1/v2)
server/mines.mjs       — минёр и курочка
server/crash.mjs       — краш, серверное время, ленивое закрытие раунда
server/instant.mjs     — рулетка, апгрейд, плинко
server/stats.mjs       — ожидание и дисперсия раундов, сводная статистика
server/repository.mjs  — адаптер хранения и последовательные транзакции
server/index.mjs       — HTTP API и статический интерфейс
web/app/game.tsx       — оболочка: меню, история, статистика, честность, админка
web/app/*-game.tsx     — экраны игр
web/lib/verify*.ts     — независимые браузерные проверки (Web Crypto)
tests/                — математика, статистика, хранение, конкуренция, HTTP
```

Данные: `data/state.json`, исключён из Git. Изменения сериализуются над копией
состояния, запись — временный файл и rename. Ошибка откатывает изменение в памяти.
Повтор с тем же requestId не списывает снова; изменённые параметры с тем же ID отклоняются.

Файловый адаптер рассчитан **на один процесс и общий демо-кошелёк**. История хранится
целиком, запись O(n), несколько серверов с одним файлом недопустимы.
Для PostgreSQL: users, wallets, ledger_entries, bets, seed_sessions, game_configs,
config_audit. Списание, выплату, выделение nonce и ставку объединить одной транзакцией
с блокировкой кошелька/seed-сессии, уникальными (user_id, request_id) и
(seed_session_id, nonce). Добавить пагинацию и отдельные seed-сессии пользователей.
Новые игры подключаются через слой service и API.

До публичного запуска нужны аккаунты, серверные роли, защищённая админка,
лимиты запросов, полноценный денежный журнал, резервные копии и управление секретами.
Скрыть вкладку недостаточно. По умолчанию сервер и публикация порта Compose доступны
только на loopback. Это не сертифицированное казино и не система реальных платежей.

## API

- `GET /api/health` — готовность процесса.
- `GET /api/state` — баланс, условия, commitment, 100 последних ставок, раскрытые seed.
- `POST /api/bets` (Hi-Lo) — requestId, amount (сотые CR), direction, threshold, clientSeed,
  version, commitment; возвращает round и state.
- `POST /api/seeds/rotate` — раскрыть seed и начать сессию.
- `POST /api/admin/config` — rtpBps (8000–9900), version.
- `POST /api/ladder/start` — requestId, amount, rocks (1–7), clientSeed, version, commitment.
- `POST /api/ladder/step` — roundId, step, column (в пределах ширины ступени).
- `POST /api/ladder/cashout` — roundId, steps.
- `POST /api/mines/start` — …, bombs (1–24); `/api/mines/step` — roundId, step, cell (0–24);
  `/api/mines/cashout` — roundId, hits.
- `POST /api/chicken/start` — …, difficulty (easy/medium/hard/daredevil);
  `/api/chicken/step` — roundId, step; `/api/chicken/cashout` — roundId, hits.
- `POST /api/crash/start` — …, target (сотые, 101–100000) или null;
  `/api/crash/cashout` — roundId. `GET /api/crash` — активный и последний раунд, serverNow.
- `POST /api/roulette/spin` — …, bets: [{ target: "red" | "black" | 0–14, amount }].
- `POST /api/upgrade` — …, amount, target (сотые CR).
- `POST /api/plinko` — …, amount, rows (8–16), risk (low/medium/high).

Все старты принимают requestId, clientSeed, version и commitment; повтор с тем же
requestId возвращает тот же раунд и не списывает снова.

POST принимает JSON; чужой браузерный Origin отклоняется. Это не аутентификация.

## Проверки

```sh
npm test
npm run check
npm run build
```

Тесты покрывают 10 000 исходов Hi-Lo, таблицы множителей с референсов, точный RTP
всех таблиц плинко, распределения (χ² для рулетки, плинко, камней лестницы; частоты краша),
ожидание и дисперсию пошаговых игр для фиксированных стратегий, калибровку z-оценки,
идемпотентность, откат/сериализацию транзакций, перезапуск, совпадение браузерных
Web Crypto проверок с сервером для всех игр и HTTP-маршруты.
Опциональный WebMCP `open_fairness` открывает вкладку честности в поддерживающем браузере.
